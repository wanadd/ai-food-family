# Physical V2 Blueprint

## Status

Status: accepted canonical implementation blueprint.

This document distills the physical V2 design. It is not an implementation task. It does not create migrations, change models, alter databases, backfill, regenerate recipes, delete recipes, split Core, split PostgreSQL, push, merge, or deploy.

## Owner decisions

OD-01 is accepted: V2 uses one versioned migration authority at the V2 boundary. The intended implementation mechanism is Alembic because the backend uses SQLAlchemy/FastAPI and no material repository blocker is known. Alembic must still be installed, configured, baselined, and validated only in a future wave-scoped implementation task.

Schema authority transition:

```text
LEGACY_SCHEMA_AUTHORITY
-> VERIFIED_BASELINE
-> SINGLE_V2_VERSIONED_MIGRATION_AUTHORITY
```

No two systems may own the same V2 object. The current deterministic bootstrap remains current-state evidence until V2 migration authority is implemented and accepted.

OD-02 is accepted: legacy recipe public-ID compatibility is bounded and includes archive fallback for unmapped legacy recipes.

```text
LEGACY_RECIPE_ID
-> compatibility resolver
-> canonical mapping if available
-> archive fallback if unmapped
```

Legacy recipe deletion remains unauthorized.

## Core physical model

Initial V2 Core includes:

- `core_accounts`
- `core_auth_identities`
- `core_persons`
- `core_households`
- `core_memberships`
- `core_person_relationships`
- `core_permission_grants`
- `legacy_id_mappings`

New canonical Core IDs are UUIDv7 for account, person, household, and membership. UUIDv7 values are generated by an application-side helper and stored as PostgreSQL `uuid`. `created_at` remains explicit and authoritative for business creation time.

Account is not Person. Person is not Membership. A dependent Person may exist without Account. A Person may have multiple Memberships. Telegram identity is an AuthIdentity, not Person identity.

`birth_date` is restricted CorePerson PII. Age and age_months are derived at evaluation time through a controlled projection such as PersonAgeContext.

## Food physical model

FoodProfile is Food-owned and person-scoped. It is represented by a FoodProfile root plus typed Food facts and dedicated constrained tables where needed. It does not recreate a global domain-heavy PersonProfile.

Knowledge states preserve at least `UNKNOWN`, `NOT_PROVIDED`, `KNOWN_NONE`, and `KNOWN_PRESENT`. Unknown must not become false, zero, or safe.

The Food ontology separates FoodIdentity, FoodCompositionFact, FoodSafetyFact, PackagedProduct, ProductInstance, recipe/version, plan, cooking, consumption, pantry, shopping, receipt/OCR observation, and evidence source.

Generic food is not packaged product. Packaged product is not actual product instance. Product-label truth must not be inferred from generic food identity.

## Recipe and media

Target recipes use stable `Recipe` identity and immutable/versioned `RecipeVersion` content with structured ingredients, steps, tags, safety claims, media links, lifecycle state, and Gold V3 validation metadata.

Legacy 174 recipes are not canonical V2 content. They remain transition/archive data. Favorites, history, menu references, cooking history, media, and supported deep links remain resolvable during the bounded compatibility window.

Recipe media uses reusable MediaAsset and derivative records. Domain identity is not bound to one storage path or provider.

## Evidence and RI-2

Evidence remains the deterministic authority chain:

```text
RegulatorySource
-> SourceSnapshot
-> EvidenceRecord
-> EvidenceClaim
-> Applicability
-> ReviewDecision
-> RuleEvidenceLink
-> ProductionRule
-> RuntimeDecision
```

AI is not evidence authority.

RI-2 physical design is accepted: NutritionTarget active effective periods require PostgreSQL-level non-overlap protection, preferably range-backed GiST exclusion on person/type/context/effective range. RI-2 runtime status remains `BLOCKING_BEFORE_BACKFILL` until implementation proves the constraint on PostgreSQL, rejects invalid overlap, accepts adjacent/open-ended valid intervals, and passes rerun/idempotency.

NutritionTarget backfill remains blocked.

## Planning through health

Planning uses Plan, Revision, Slot, and explicit Participants/Portions. Explicit empty/free slots remain explicit and cannot be silently reanimated by fallback enrichment.

Shopping preserves demand provenance. Pantry separates FoodIdentity, PackagedProduct, ProductInstance/inventory lot, quantity, expiry, movement history, and provenance.

Receipt/OCR follows staged truth: raw media, OCR/extraction observation, line/classification, candidate match, confirmed match, canonical mutation. OCR or AI observation is not canonical product truth.

Planned, cooked, and consumed are distinct. Cooking captures actual preparation/process/substitution facts. Consumption is Person-scoped actual intake. Health is derived and must preserve completeness/version semantics.

## AI, ImportantDate, entitlements, notifications, jobs

AI may propose, parse, classify, generate, and explain. It is not identity, evidence, medical rule, payment, entitlement, or canonical persistent user-fact authority. Unrestricted AI memory is not introduced.

ImportantDate/PersonalEvent remains `LATER_NOT_INITIAL_V2_MIGRATION`.

Entitlements use namespaced capability grants. Billing truth is not entitlement consumption. Notifications flow from domain trigger to NotificationIntent, preferences/policy, delivery, and channel adapter. Telegram is a channel adapter.

Jobs/outbox use DB-backed durable outbox/job records with retry, idempotency, observability, availability scheduling, failure state, and transactional semantics where required.

## Module and migration DAG

The module DAG is acyclic. Core does not depend on Food. Food modules depend on explicit Core contracts. Health does not become source of truth for Consumption. AI does not become Evidence authority.

Physical migration has 15 stages:

1. prerequisites and owner acceptance;
2. schema authority foundation;
3. Core roots;
4. FoodProfile;
5. ontology/evidence/product;
6. NutritionTarget RI-2;
7. recipe/version/media;
8. planning;
9. shopping/pantry;
10. cooking/consumption;
11. health projections;
12. notifications/entitlements/jobs;
13. compatibility adapters/API cutover;
14. authority switch;
15. legacy retirement.

Implementation has 11 waves. Wave 01 establishes the versioned migration authority foundation, reference enum contracts, UUIDv7 helper, and PostgreSQL migration acceptance harness only. Later waves remain unauthorized until separately scoped and accepted.

## Compatibility and retirement

Legacy migration classes are `AUTO_MIGRATE`, `AUTO_MIGRATE_WITH_PROVENANCE`, `RECALCULATE`, `RECONFIRM`, `ARCHIVE_ONLY`, and `DO_NOT_MIGRATE`.

Ambiguous allergy absence, medical certainty, DOB, pregnancy state, OCR matches, and AI/free-text inference must not migrate as deterministic certainty.

Compatibility adapters are required for User/Profile, Family, Recipe, Menu, Shopping, Pantry, Health, and Receipt/OCR. They must not become permanent second domain models. Each compatibility layer requires retirement criteria.

## Implementation block

Wave 01 implementation is limited to the migration foundation and does not authorize Core roots, FoodProfile, Recipe V2, planning, shopping, pantry, cooking, consumption, health, ImportantDate, backfill, production deployment, or legacy deletion.
